# Бенчмарки

План и правила для всех бенчей: `docs/BENCHMARKS_PLAN.md`. Датасеты и лицензии: `DATASETS.md`.

**Общая обвязка** (`common/`, задача 1 плана). `stats`: 95% ДИ бутстрэпом (2000 повторов, seed 0), кластерный по группам и парный для разницы двух условий на одних треках. `manifest`: JSONL-манифесты с проверкой полей и отчётом о покрытии. `runner`: инструменты через `ah.runner.Runner` на одноразовом хранилище, выходы кэшируются по sha256 входа, инструменту и параметрам, время каждого вызова записывается. `results`: `tracks.csv` и `summary.json` с метаданными прогона (коммит, устройство, бэкенды, ревизии моделей, sha256 манифеста, покрытие). `speech`: речевые метрики (Whisper WER/CER, DNSMOS, UTMOS22, ECAPA, SI-SDR), перенесены из бенчмарка denoise v2 (Jamal) с теми же ревизиями; работают в отдельном окружении `uv sync --project benchmarks/envs/speech`. Скрипт прямо в `benchmarks/` импортирует `from common import stats`; скрипт в подпапке сначала добавляет `benchmarks/` в `sys.path`.

## Агент: понимает ли запрос и тянет ли нужные инструменты (2026-10-23)

### Сводка (скорер v2, 2026-10-23)

**Скорер v2.** Скорер v1 проверял только параметры, указанные в эталоне, и не учитывал язык ответа. v2:
- сравнивает `trim` по фактическому диапазону с умолчаниями: лишний `start_s=5` при эталоне «`end_s=197.4`» теперь ошибка;
- запрещает `analyze` выключать то, о чём просили (поле эталона `needs`);
- проверяет входы по позиции шага;
- включает язык ответа в «план верный». Старая метрика без языка называется `plan_ok`;
- узнаёт больше честных отказов («none of our tools can…», «ни один из инструментов не умеет…»);
- правильно распознаёт итальянский и испанский.

Изменения в эталонах после заморозки только ужесточают проверку: `needs` в 15 задачах, позиционный вход в `chain-09`, без голого «минор» в `history-02`. Все прогоны пересчитаны v2. Цифры в разделах ниже посчитаны v1 и оставлены для истории.

- 73 задачи из 100 требуют одного инструмента, 11 — ни одного, 6 — двух, и только 10 — цепочки из 3–4 шагов;
- состояний трека 7, и 56 задач сидят на одном из них (`song_fresh`). Пять попыток одного запроса проверяют стабильность, а не добавляют сценарии;
- в режиме plan модель видит текст и метаданные, аудио не слышит;
- метрика исполнения гоняет план на коротких синтетических клипах и проверяет наличие и непустоту артефактов, но не их качество.

Следующий шаг для оценки, которую можно предъявлять: запросы от независимых пользователей и сквозной тест с проверкой качества на размеченном аудио (задача 8 плана).

**Что меряем.** Настоящий `Agent.message` харнесса (системный промпт, каталог инструментов из реестра, `validate` с одним повтором), тот же путь, что за `ah ui`. Подменён только `track_data`: он берётся из фикстур, собранных функцией `ah.agent.track_data` по настоящему хранилищу (`benchmarks/agent/fixtures/`: свежая песня, песня с анализом, после separate, выбран вокал, диктофон, 45-минутное интервью). Инструменты не запускаются, результат прогона это план. **100 задач** (`benchmarks/agent/tasks/plan.jsonl`), по 10 на каждую из 10 категорий, ru и en пополам, каждая гоняется 5 раз. План верный, если последовательность инструментов входит в допустимые, входы подключены правильно (restore на `1.vocals`, а не на `track`), параметры совпадают (trim с допуском 0.1 с), нет запрещённых инструментов, на неподдерживаемом сказано «пока нельзя», а если ответ уже есть в данных, он в ответе. Всё проверяется детерминированно, без LLM-судьи. ДИ 95% бутстрэпом по задачам.

**Что поменяли** (`src/ah/agent.py`):

- **Язык.** Одна формулировка в промпте не помогла: с правилом «отвечай на языке запроса» flash без thinking стал отвечать на английские запросы по-русски. Помогло решить очевидные случаи кодом: `reply_language()` смотрит на запрос (кириллица → русский или украинский, английские служебные слова в ASCII → английский), а модель получает тег `<reply_language>` вне текста пользователя. Если язык неочевиден (итальянский, немецкий), тега нет и решает модель, как раньше. Тот же язык передаётся в вызов итогового сообщения. Все запросы бенча попадают в очевидные случаи, поэтому ответ пользователю на третьем языке этот бенч не мерит.
- **Обрезка.** «Режь только когда просят обрезать, укоротить или убрать тишину; тишина или длина в данных не повод».
- **separate на речи.** «separate для песен; диктофон, интервью, подкаст чистить denoise или restore напрямую; песню от речи отличать по словам пользователя и имени файла».
- **Входы.** «Версии из истории (вокал от прошлого separate) входом быть не могут; если выбран микс, а нужен вокал, сначала separate». Это лечит «почисти вокал» на треке, где separate уже делали.

**Пустой `trim` отклоняется в `validate`** (2026-10-23, `results/*-trimcheck`). После правки промпта модель иногда обещала обрезку и присылала `trim` без параметров: шаг, который ничего не меняет (flash без thinking 2 из 5 на `multi-08`, flash с thinking 1 раз). Теперь `validate` отклоняет `trim` без `start_s`, `end_s` и без `silence: true`, и модель получает повтор с объяснением. На новом прогоне правило сработало один раз на 1000 попыток flash (`multi-04`: «отрежу первые 10 секунд» без `start_s`), повтор дал верный план. Принятых пустых `trim` больше нет. Точность в пределах шума: flash с thinking 1.0 (было 0.998), flash без thinking 0.96 (было 0.974, парная разница −0.014 [−0.034, 0.004], колебания в «неподдерживаемом»). **v4-pro на этом прогоне не досчитан**: на счёте DeepSeek кончились деньги (402 Insufficient Balance, до этого 429), 127 из 500 попыток не дошли до модели; результаты в git не положены.

**Что осталось:**

- **Лишний шаг при честном отказе** (flash без thinking): «транскрибируй интервью» → `denoise`, «master for Spotify» → `inspect`. Отказ честный, но в плане появляется шаг, о котором не просили.
- **Время.** Один раз из пяти «Take 1:00 to 2:30» → `end_s = 90` (flash без thinking).

**Ошибки до правки**, для истории: ответы на английские запросы приходили по-итальянски, по-немецки, по-испански, по-португальски, по-польски, по-турецки, по-венгерски (один раз с китайским иероглифом); «убери гул из интервью» → `separate > denoise`; «убери шум с диктофона» → `trim > denoise`, потому что в данных 18% тишины; «почисти вокал от шипения» на треке, где separate уже делали → `denoise` прямо на миксе.

По категориям (верный план, замороженный скорер): самые слабые места у flash — **арифметика 0.76, цепочки 0.74, ловушки в имени файла 0.84**; у v4-pro — **трудное неподдерживаемое 0.80 (0.94 с поправкой на отказы), ловушки в имени файла 0.82**. Отрицания, косвенные намерения, языки, продолжение диалога, опечатки: 0.98–1.0 у обеих моделей.

**Что нашлось:**

- **flash не кладёт `params` в шаг.** «Убери последние 15 секунд» → в `why` написано «оставить 0–197,4 с», а в шаге поля `params` нет вообще. `validate` отклоняет пустой `trim`, повтор приходит такой же. Так 33 попытки из 500. Причина в схеме `submit_plan`: `params` там необязательное поле с подсказкой «leave out for defaults». Чинить схемой (параметры каждого инструмента прямо в схеме шага или обязательное `params` у `trim`), а не промптом.
- **Модель верит имени файла больше, чем пользователю.** «Какой темп у этой песни?» на файле `voice_memo_0412` → «это голосовая заметка, темп для речи бессмыслен». «Clean up the singing in this track» → `denoise` на всём миксе без `separate`. У обеих моделей.
- **Арифметика и направление обрезки.** v4-pro на «убери первые 8 секунд» дважды из пяти оставил ровно эти 8 секунд (`start_s: 0, end_s: 8`), на «последние 5 минут интервью» один раз округлил 45:12 до 45:00.
- **Язык без подсказки.** На «acapella pls» (английских служебных слов нет, кодовый детектор молчит) ответы приходили по-итальянски, португальски, французски, испански. Дважды v4-pro ответил по-немецки на английский запрос, хотя тег `English` был.
- **Неподдерживаемое** v4-pro отрабатывает честно (с поправкой на скорер 0.94), но на «разбей на drums, bass, vocals и other» дважды спросил «запустить разделение на два?» вместо того, чтобы сделать выполнимую часть.

**Выполнение плана** (2026-10-23, `benchmarks/agent/execute.py`, `results/agent-heldout-*/exec/`). Соответствие запросу проверяет только план. Здесь каждый записанный план отложенного прогона реально выполняется шаг за шагом через `Runner`: окружения инструментов, приведение к 44.1 кГц стерео, передача выходов от шага к шагу. Каждый шаг проверяется на то, что обязан оставить его инструмент: все выходы из реестра, аудио непустое, конечное и не тише −60 dBFS по пику, у `analyze` в отчёте есть BPM, у `inspect` есть уровни, у `trim` длина совпадает с запрошенным диапазоном. Клипы короткие, чтобы `separate` и `restore` укладывались в CPU: 20 с песни (синтетический минус на 120 BPM + голос из синтеза речи macOS), 15 и 30 с речи из синтеза речи с гулом и шипением. Времена `trim` масштабируются под длину клипа в той же пропорции, что клип к фикстуре, поэтому «внутри файла» и «за его концом» остаются как в плане. Одинаковые вызовы кэшируются (`data/derived/agent-exec`, в git не идёт). Качество выхода (насколько чист вокал, верен ли BPM) здесь **не** мерится: для этого нужны размеченные датасеты (задача 8 плана).

**Что нашлось:**

- **`validate` пропускает недопустимые значения параметров.** v4-pro на «ладно, тогда хотя бы аккорды сними» (`history-05`, 1 попытка из 5) прислал `analyze` с `beats: null`. `validate` сверяет только имена параметров, план прошёл и засчитан как верный, а на исполнении `analyze` упал на валидации pydantic. Исправление: в `validate` прогонять `params` через модель параметров инструмента, тогда модель получит повтор.
- **Первая версия метрики была слабой, исправлено.** В первом прогоне вместо голоса был синтезированный тон с вибрато. `separate` оставил его в инструментале, вокальный стем вышел с пиком −46 dBFS, после `denoise` −105 dBFS. Проверка «аудио непустое» такую тишину пропускала, и вокальные цепочки «исполнялись» без результата. Видно это стало только на `trim(silence)` поверх тишины: «nothing above −50 dBFS». После замены на настоящий голос и проверки на тишину стемы стали −10 dBFS (вокал) и −6 dBFS (минус), а этот сбой ушёл. Цифры первой версии: flash 0.993, v4-pro 0.986.

Почему исполнение около 1.0, а сквозной успех ниже: почти всё, что ломается, ломается на этапе плана (неверный инструмент, пустой `trim`, доверие имени файла). Планы, которые прошли `validate`, исполняются, за одним исключением выше. Оговорки: CPU, короткие синтетические клипы, один голос из синтеза речи. На настоящем материале длинных треков и на GPU-бэкенде (`remote`) не гонялось.

## analyze на GuitarSet (2026-10-21)

**Что гоняли.** `ah_analyze.AnalyzeTool` как есть (тот же код, что за `ah analyze`), трекер битов madmom. Beat This! не проверен: хост чекпоинта `cloud.cp.jku.at` в день прогона отдавал 503 на стороне апстрима. Датасет GuitarSet 1.1.0, все 360 отрывков, микрофонная запись (`audio_mono-mic`), около 3 ч аудио. Метрики считает `mir_eval` 0.8.2. CPU, 4 процесса, около 35 минут wall time; один процесс работает примерно в 0.77 от реального времени.

**Лицензия датасета.** GuitarSet распространяется под CC BY 4.0 (Zenodo 3371780), можно и в коммерческих целях, нужна ссылка на Xi et al., ISMIR 2018. В репозиторий кладём только метрики (`results/`), аудио не кладём. Модели madmom по-прежнему CC BY-NC-SA 4.0. Утечки нет: модели madmom обучены до выхода GuitarSet (2018).

**Как читать.** GuitarSet это соло-гитара без барабанов и баса: comp (аккомпанемент) и solo (мелодия поверх подложки, которой в записи нет). Без ритм-секции это тяжёлый случай для любого трекера, так что это не оценка madmom «вообще», а оценка того, как наш analyze поведёт себя на гитарной записи. Темп, биты и тональность берутся из задания игроку (метроном и лид-шит). Аккорды comp сравниваются с транскрипцией сыгранного. Аккорды solo в таблице для полноты: в аудио нет аккомпанемента, так что это не оценка модели аккордов.

### Паттерны ошибок

- **Темп: 236 из 360 точно.** Остальные ошибки почти все «музыкальные», а не мусор: 31 удвоение, 27 половин, 36 отношений 3:2 или 2:3 и только 30 совсем мимо. Удвоение чаще на медленных треках (25 из 96 в slow, меньше 100 BPM), половина на быстрых и в джазе (14 из 72; 200 BPM определяется как 100). Отношение 2:3 сидит в фанке и роке (114 → 78, 130 → 86): трекер цепляется за синкопированные группы шестнадцатых. В singer-songwriter наоборот, 3:2 (68 → 102, 17 из 72): похоже на триольное или 12/8 ощущение.
- **Тональность: главная слабость.** Мажор точно в 55% случаев, минор только в 28%. В 50 из 120 минорных треков модель называет параллельный по ключевым знакам мажор (relative), то есть ноты угаданы, а тоника нет. Confidence из ответа полезен: при confidence выше 0.7 точность 70%, ниже 0.3 только 22%. Текущий порог предупреждения 0.5 выбран разумно.
- **Биты: фаза на босса-нове.** В 26 треках трекер держит правильный период (AMLt выше 0.8), но ставит биты на слабые доли (F ниже 0.2). 13 из них босса-нова, 8 рок. Отсюда же низкие сильные доли: 0.41 в целом.
- **Аккорды на comp хорошие:** majmin 0.85, на роке и singer-songwriter 0.93. Хуже всего фанк (0.66): короткие стаккатные аккорды, много пауз. В джазе root 0.71 против majmin 0.82, потому что модель знает только мажор и минор, а там септаккорды, hdim7 и пропущенные ступени.
- **Solo:** всё хуже, а аккорды бессмысленны, потому что в одноголосой мелодии их нет. Если агенту дадут соло-партию, ответ analyze про аккорды стоит не показывать или явно помечать.
- **Исполнитель 05** заметно хуже остальных по темпу (Acc1 0.45 против 0.63–0.77) и битам (F 0.48). Это, скорее всего, манера игры (свободнее с темпом), а не баг.

### Что из этого следует

1. Темп отдавать вместе с `bpm_alternatives`, как сейчас. Стоит добавить туда и ×2/3, ×3/2: это 10% треков.
2. Тональность на одиночной гитаре ненадёжна, особенно минор. Варианты: показывать две верхние гипотезы, если между ними relative-пара; или брать тонику из аккордов (последний и самый длинный аккорд), это дешёвая эвристика.
3. Сильные доли и размер на одиночной гитаре почти случайны, агенту стоит подавать их как низкодоверенные.
4. Beat This! ещё предстоит сравнить на этом же наборе: `--beats beat_this` с локальным `AH_BEAT_THIS_CHECKPOINT`.

## Темп и биты на Ballroom и GiantSteps (Jamal)

Скрипт `benchmarks/tempo.py`, тесты в `tests/test_tempo_benchmark.py`. Результатов прогона в репозитории пока нет. Ниже оригинальная инструкция автора; команды запускать из корня репозитория.

This benchmark evaluates `ah analyze` separately on Ballroom and GiantSteps.
It prepares JSONL manifests for later GPU training, but does not train a model.
Neither dataset supplies chord reference labels, so this benchmark measures tempo
and, for Ballroom, beat/downbeat timing only.

### Data

- Ballroom: [audio archive](http://mtg.upf.edu/ismir2004/contest/tempoContest/data1.tar.gz)
  (~1.5 GB, expected MD5 `2872a3e52070bc342a4510a95e2fa0b8`) and
  [beat annotations](https://github.com/CPJKU/BallroomAnnotations). Unpack the
  audio archive to any local directory. The loader searches subdirectories by
  audio basename; duplicate basenames are reported as an error.
- GiantSteps: [tempo annotations and official folds](https://github.com/GiantSteps/giantsteps-tempo-dataset).
  Audio is available as Beatport previews through the dataset's `audio_dl.sh`
  (~1 GB). Keep the MP3 files in its `audio/` directory, or point `--audio` to
  another directory. Three `0.0` v2 labels are excluded.

Source audio may have separate terms from the annotation repositories. Keep
downloaded audio outside Git. `tmp/` is ignored by this project.

### Prepare

From the repository root (PowerShell examples):

```powershell
git clone --depth 1 https://github.com/CPJKU/BallroomAnnotations.git tmp/bench-datasets/BallroomAnnotations
git clone --depth 1 https://github.com/GiantSteps/giantsteps-tempo-dataset.git tmp/bench-datasets/giantsteps-tempo-dataset

python benchmarks/tempo.py prepare ballroom `
  --annotations tmp/bench-datasets/BallroomAnnotations `
  --audio tmp/bench-datasets/ballroom-audio `
  --output tmp/bench-ballroom.jsonl

python benchmarks/tempo.py prepare giantsteps `
  --annotations tmp/bench-datasets/giantsteps-tempo-dataset `
  --audio tmp/bench-datasets/giantsteps-tempo-dataset/audio `
  --output tmp/bench-giantsteps.jsonl
```

The command reports how many audio files it found. Manifest records with
missing audio remain in the file, so a run can report coverage honestly.
Run `prepare` again after adding audio, because manifests contain resolved
audio paths.
Ballroom records use `split: all`. GiantSteps retains the official fold ID;
fold 1 is test, fold 2 is validation and folds 3–10 are training candidates.
The benchmark's published full-dataset result uses `--split all`; a trained
model must be evaluated on the held-out `--split test` subset instead.

### Evaluate

Use the `tools/analyze` Python environment (with `ah-analyze`, Beat This! and
madmom installed). The main project environment may have different PyTorch
versions. On Windows, for example:

```powershell
tools/analyze/.venv/Scripts/python.exe benchmarks/tempo.py run `
  --manifest tmp/bench-ballroom.jsonl --output tmp/bench-ballroom-results `
  --beats beat_this --device cpu --limit 10

tools/analyze/.venv/Scripts/python.exe benchmarks/tempo.py run `
  --manifest tmp/bench-giantsteps.jsonl --output tmp/bench-giantsteps-results `
  --beats beat_this --device cuda --split test --limit 10
```

Remove `--limit` for complete runs. `--device cuda` selects an NVIDIA GPU for
Beat This! inference if PyTorch can see it. It does not enable training. The
`madmom` beat tracker runs on CPU even when `--device cuda` is given.

Each output directory contains `results.jsonl` and `summary.json`. Acc1 is
within 4% of the annotated BPM. Acc2 also accepts half or double tempo.
Ballroom beat and downbeat F1 use a 70 ms matching window within the annotated
interval. Failed/missing audio files count toward coverage, never accuracy.
Keep separate output directories for each dataset and tracker.
Long runs save each track immediately. Reuse the same command with `--resume`
after an interruption; it skips completed tracks and retries failed ones.
